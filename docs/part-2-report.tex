\begin{abstract}
We formulate cross-domain Text-to-SQL and build an execution-based
evaluation harness for Spider (multi-table, unseen databases) and
WikiSQL (single-table). Two classical baselines are compared: a
deterministic template parser and a two-stage pointer-generator BiLSTM
sequence-to-sequence model. The headline comparisons use the official
Spider evaluator (exact-set match and execution accuracy) with
database-clustered 95\% confidence intervals, paired McNemar tests and
Holm correction. Our own harness supplies the diagnostic breakdowns.
Every inference fix was developed on Spider dev and frozen before a
single run on the held-out Spider test set (2,147 questions, 40
databases disjoint from train and dev).

On \textbf{Spider test}, the template parser reaches \textbf{9.5\%
official execution accuracy} and \textbf{6.7\% official exact-set
match}, against 7.2\% and 5.5\% for the LSTM. The template's lead on
execution accuracy (2.3 points) is significant by McNemar (Holm p =
0.008) but borderline under a database-clustered bootstrap (p = 0.045
unadjusted, 0.14 adjusted), and the two do not differ significantly on
exact-set match. Both baselines almost entirely fail on the stated core
objective, multi-table queries (1.83\% {[}0.9\%, 3.6\%{]} strict EX for
the LSTM on dev). The LSTM's failures are overwhelmingly schema-linking
errors: identifier recall is 40.4\%, 690 of 746 invalid queries
reference a nonexistent column, and its copy gate switches to copying
correctly but points at the wrong schema element. Per-epoch dev-loss
curves from replication runs of the same recipe show overfitting after
about three Spider epochs, although training continued for 25. On
WikiSQL we found and fixed a harness defect: gold SQL named columns that
the database stores as \texttt{col0…colN}, so 71\% of gold queries
silently returned nothing. With it fixed, the Stage-1 LSTM's near-total
failure turns out to be a rendering defect rather than catastrophic
forgetting, and fixing the rendering raises its execution accuracy from
5.76\% to 17.15\%, far above the template's 2.65\% (McNemar p
\textless{} 10\textsuperscript{-200}).
\end{abstract}

\section{Introduction to the NLP
Task}\label{introduction-to-the-nlp-task}

\subsection{Motivation}\label{motivation}

Relational databases hold most structured enterprise and scientific
data. Writing SQL against them requires knowing SQL syntax, relational
operations (projection, selection, grouping, joins) and the exact table
and column names of each schema. Text-to-SQL removes this barrier by
translating a natural-language question into an executable query, giving
non-technical users conversational access to structured data.

\subsection{Core challenges}\label{core-challenges}

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Schema linking.} Questions rarely use exact identifiers. In
  \emph{``Which airports are in Los Angeles?''}, the phrase ``airports''
  must be linked to table \texttt{airports}, ``Los Angeles'' to a value
  of column \texttt{City}, and the answer to \texttt{AirportName}.
\item
  \textbf{Compositional structure.} Multi-table queries need joins along
  foreign keys, nested subqueries, \texttt{GROUP\ BY}/\texttt{HAVING},
  ordering and set operations.
\item
  \textbf{Cross-domain generalisation.} Test databases are unseen during
  training, so the model cannot memorise identifiers. It must read the
  schema supplied at inference time.
\item
  \textbf{Executable validity.} A single unknown column or unquoted
  literal makes SQLite reject the query, so a nearly-correct token
  sequence can still score zero.
\end{enumerate}

\subsection{Formulation}\label{formulation}

Given a question \(Q=(q_1,\dots,q_m)\) and a schema
\(\mathcal{S}=(\mathcal{T},\mathcal{C},\mathcal{E})\) of tables, columns
and foreign-key edges, produce SQL \(Y=(y_1,\dots,y_n)\) such that
executing \(Y\) on the database returns the intended result:
\[\hat{Y}=\arg\max_Y \prod_{t=1}^{n} P(y_t\mid y_{<t},Q,\mathcal{S}).\]

\section{Literature Survey: Why the Problem
Matters}\label{literature-survey-why-the-problem-matters}

\subsection{Rule-based semantic
parsing}\label{rule-based-semantic-parsing}

PRECISE (Popescu et al., 2003) maps words to database elements through
bipartite matching and guarantees precision on the questions it accepts,
but its recall drops sharply outside its patterns. SCFG (Wong and
Mooney, 2007) and CCG (Zettlemoyer and Collins, 2005) parsers induce
logical forms but need domain lexicons and do not transfer across
schemas.

\subsection{Neural sequence-to-sequence
parsing}\label{neural-sequence-to-sequence-parsing}

Encoder--decoder LSTMs (Sutskever et al., 2014) with attention (Bahdanau
et al., 2015) treat Text-to-SQL as translation. Two weaknesses matter
here. First, identifiers and literals are often out of vocabulary.
Second, unconstrained decoders emit ungrammatical or schema-inconsistent
SQL.

\subsection{Pointer and copy
mechanisms}\label{pointer-and-copy-mechanisms}

Pointer Networks (Vinyals et al., 2015) and Pointer-Generator Networks
(See et al., 2017) mix a vocabulary distribution with a copy
distribution over the input:
\[P(w)=p_{\text{gen}}P_{\text{vocab}}(w)+(1-p_{\text{gen}})\sum_{i:x_i=w}a^t_i .\]
On WikiSQL, Seq2SQL (Zhong et al., 2017) and SQLNet (Xu et al., 2017)
combine pointing with sketch-based slot filling.

over 200 databases in 138 domains, split so that test databases are

\textbf{Query-structure categories} (\texttt{\_query\_structure} in
\texttt{data/spider.py}) are rule-based on the gold SQL text. A query
goes to \emph{multi-table} if it contains \texttt{JOIN}, \texttt{UNION},
\texttt{INTERSECT} or \texttt{EXCEPT}. Otherwise it goes to \emph{other
(nested)} if it contains more than one \texttt{SELECT}, and otherwise to
\emph{single-table}. The first matching rule wins, so a query with both
a join and a subquery is counted as multi-table, and set operations
count as multi-table even over one table. Dev has 544 single-table, 438
multi-table and 52 nested examples.

\subsection{Schema serialisation}\label{schema-serialisation}

\texttt{data/schema.py} serialises each schema deterministically, with
tables and columns sorted:

\begin{Shaded}
\begin{Highlighting}[]
\NormalTok{database: concert\_singer}
\NormalTok{table: singer}
\NormalTok{columns:}
\NormalTok{  {-} Age [number]}
\NormalTok{  {-} Country [text]}
\NormalTok{  {-} Singer\_ID [number] [PRIMARY KEY]}
\NormalTok{foreign\_keys:}
\NormalTok{  {-} singer\_in\_concert.Singer\_ID {-}\textgreater{} singer.Singer\_ID}
\end{Highlighting}
\end{Shaded}

The encoder input is
\texttt{\textless{}bos\textgreater{}\ question\ \textless{}schema\_sep\textgreater{}\ schema\ \textless{}eos\textgreater{}},
where both parts are tokenised by the regex lexer in
\texttt{lstm/preprocessing.py}. Column \emph{types} (\texttt{text},
\texttt{number}) and markup words (\texttt{table}, \texttt{columns})
become ordinary copyable source tokens. Section d.8 shows this was the
largest single source of invalid SQL.

\subsection{Tokenisation and
vocabulary}\label{tokenisation-and-vocabulary}

\begin{itemize}
\tightlist
\item
  \textbf{Lexer.} It keeps SQL punctuation and operators, splits
  \texttt{t1.col} into \texttt{t1\ .\ col}, upper-cases SQL keywords and
  lower-cases everything else. A quoted literal becomes one unquoted,
  lower-cased token
  (\texttt{\textquotesingle{}United\ States\textquotesingle{}} →
  \texttt{united\ states}).
\item
  \textbf{Vocabulary.} Every token in the Stage-1 and Stage-2
  \emph{training} questions, schemas and SQL, with no frequency
  threshold: \textbf{102,463 types} (\texttt{training\_meta.json}). Dev
  and test are never read when building the vocabulary.
\item
  \textbf{Copy targets.} Each example extends the vocabulary with its
  out-of-vocabulary source tokens. A gold SQL token resolves to the
  fixed vocabulary first, then to a source copy, else to
  \texttt{\textless{}unk\textgreater{}}.
\end{itemize}

Three effects are visible. Punctuation is dropped from the question. The

surface form from the question at inference. The schema's column
\emph{types} (\texttt{text}) sit in the encoder input right next to the
column names.

\emph{generated} from the fixed vocabulary. On dev and test, 8.7\% and
7.7\% of target tokens can \emph{only} be produced by copying: unseen
table names, column names and values. Is the copy path still learned?
The gate still receives gradient, because copying an in-vocabulary
source token also produces the correct token. We measured this directly
(\texttt{scripts/measure\_copy\_gate.py}, 200 dev questions,
teacher-forced). At positions whose gold token is copy-only, the gate
chooses to copy (\(p_{\text{gen}} < 0.5\)) 96.0\% of the time (mean
\(p_{\text{gen}}\) 0.04, vs 0.82 for in-vocabulary targets). But it puts
only 0.17 probability on the correct source token, vs 0.82 for
in-vocabulary targets. The pointer mechanism therefore works as a
switch: the model knows \emph{when} to copy, but not \emph{what} to
copy. This is the schema-linking failure seen throughout §d.9.

\subsection{Dataset limitations}\label{dataset-limitations}

\textbf{Spider.} Most queries appear with two paraphrased questions,
which inflates in-domain accuracy. This does not leak across our
database-disjoint splits, but it matters for the small live training
demo (§d.12). Coverage is English-only and skewed towards college,
business and entertainment schemas, and dev has only 20 databases, so
per-database variance is high. Small databases allow coincidental
execution matches (§d.9 shows one). Gold SQL follows inconsistent
conventions: \texttt{"blues"} vs
\texttt{\textquotesingle{}France\textquotesingle{}} quoting, stray
trailing semicolons and mixed identifier case. These break string match
but not execution or exact-set match. One database (\texttt{wta\_1})
stores non-UTF-8 text. Difficulty is imbalanced: 43\% of dev is medium
and only 16\% is extra-hard.

\textbf{WikiSQL.} Each question targets a single table with at most one
aggregate and \texttt{AND}-only conditions. Values are stored as text,
column names contain spaces and punctuation, and the annotations are
known to be noisy. It therefore tests pipeline mechanics rather than
compositional parsing.

\section{Method, Experiments and
Results}\label{method-experiments-and-results}

\subsection{Baseline 1: deterministic template
parser}\label{baseline-1-deterministic-template-parser}

\texttt{baselines/template.py} matches question tokens to table and
column names, detects numeric and quoted literals, comparison phrases,
aggregation cues (\texttt{how\ many} → \texttt{COUNT}, \texttt{average}
→ \texttt{AVG}), \texttt{DISTINCT} and ordering cues, and fills a
single-table template. It never generates joins. When it finds no
confident single-table interpretation it \textbf{abstains} with an empty
string. In the current code it abstains on \textbf{92 of 1,034} dev
questions (8.9\%) and 208 of 2,147 test questions. Every abstention
counts as invalid SQL. Identifiers are double-quoted only when
necessary, because the official evaluator's parser reads
\texttt{"singer"} as a string value. Apart from abstentions the template
produced no SQLite errors, so its low invalid rate reflects
conservative, single-table output.

\subsection{Baseline 2: pointer-generator
BiLSTM}\label{baseline-2-pointer-generator-bilstm}

\texttt{lstm/model.py} (values from \texttt{TrainingConfig} and
\texttt{training\_meta.json}):

\begin{itemize}
\tightlist
\item
  \textbf{Encoder:} 2-layer bidirectional LSTM. Embedding 256, hidden
  256 per direction, so 512-d concatenated states. Packed sequences.
  Training inputs are truncated at 256 tokens, which cuts 556 of the
  7,000 Spider training inputs and hides their alphabetically-last
  tables. Inference does not truncate: no dev input exceeds 242 tokens,
  but 99 of 2,147 test inputs do (maximum 278). This train/inference
  mismatch is a known limitation.
\item
  \textbf{Decoder:} 2-layer LSTM with hidden size 512, initialised from
  projected final encoder states. The input is
  \([\text{emb}(y_{t-1});\,c_{t-1}]\).
\item
  \textbf{Attention:} additive,
  \(e_{t,i}=v^\top\tanh(W_h h_i+W_s s_t)\).
\item
  \textbf{Copy gate:}
  \(p_{\text{gen}}=\sigma(W[s_t;c_t;\text{emb}(y_{t-1})]+b)\), mixing
  \(P_{\text{vocab}}\) with the attention-weighted copy distribution as
  in §b.3.
\item
  \textbf{Dropout} 0.2. \textbf{Decoding:} greedy, at most 128 tokens,
  with
  \texttt{\textless{}pad\textgreater{}}/\texttt{\textless{}unk\textgreater{}}
  masked.
\end{itemize}

\subsection{Training (HPC Job 361547)}\label{training-hpc-job-361547}

Hardware: one NVIDIA RTX PRO 6000 Blackwell MPS slice (50\%), 4 CPUs and
80 GB RAM. The whole job, training plus evaluation, took 50 min of wall
time (04:41 to 05:31 IST).

\begin{itemize}
\tightlist
\item
  \textbf{One Adam optimiser} with constant learning rate \(10^{-3}\),
  batch 64, gradient-norm clipping at 1.0, teacher forcing ratio 1.0,
  seed 42 and per-epoch shuffling with seed \(42+\text{epoch}\). There
  is no learning-rate warm-up or schedule.
\item
  \textbf{Stage 1 (WikiSQL):} 55,968 examples, 10 epochs (8,750 steps).
  Training NLL fell from 1.723 to 0.098. Saved as
  \texttt{wikisql\_checkpoint.pt}.
\item
  \textbf{Stage 2 (Spider):} 7,000 examples, 25 epochs (2,750 steps),
  continuing from Stage 1. Training NLL fell from 1.841 to 0.040. Saved
  as \texttt{spider\_checkpoint.pt}.
\end{itemize}

keeps falling. A training NLL of 0.04 alongside rising dev NLL and over

databases, not successful cross-domain transfer}. Early stopping on a
database-disjoint validation split is required for Part 3.

\subsection{Inference pipeline}\label{inference-pipeline}

The final pipeline is decode, then render, then repair. All steps
operate on the same trained weights.

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Schema-markup mask}
  (\texttt{DecodeOptions.mask\_schema\_markup}). This is new.
  Serialisation tokens (\texttt{text}, \texttt{number}, \texttt{time},
  \texttt{boolean}, \texttt{others}, \texttt{table}, \texttt{columns},
  \texttt{primary}, \texttt{key}, \ldots) are given probability 0 during
  decoding unless the current schema really has an identifier of that
  name. With base decoding, the bare token \texttt{text} appeared in 278
  of 1,034 dev predictions.
\item
  \textbf{Surface-form rendering} (\texttt{lstm/rendering.py}). This is
  new. Each decoded token is mapped back to its schema spelling
  (\texttt{School/Club\ Team} is restored and double-quoted). A value
  token after a comparison operator becomes a single-quoted literal
  using the question's original casing
  (\texttt{\textquotesingle{}France\textquotesingle{}}, not
  \texttt{\textquotesingle{}france\textquotesingle{}}). A multi-word
  literal stays one literal
  (\texttt{\textquotesingle{}United\ States\textquotesingle{}}, not
  \texttt{\textquotesingle{}united\textquotesingle{}\ states}).
\item
  \textbf{Schema-aware repair} (\texttt{lstm/sql\_repair.py}, unchanged
  in substance). It normalises spacing, re-quotes leftover bare
  literals, replaces hallucinated \texttt{FROM} tables with the schema
  table sharing the most columns, collapses single-table WikiSQL queries
  to the sole table, and balances parentheses. It now leaves the inside
  of quoted literals untouched.
\end{enumerate}

\subsection{Evaluation protocol}\label{evaluation-protocol}

\textbf{Official metrics.} Spider is scored with the official evaluator
(\texttt{taoyds/test-suite-sql-eval},
\texttt{evaluation.py\ -\/-etype\ all}) on Spider's own databases.
\emph{Exact-set match} (EM) compares SQL component by component and
ignores literal values. \emph{Execution accuracy} (EX) compares result
multisets, and row order matters only when the gold query has
\texttt{ORDER\ BY}. Test-suite accuracy (Zhong et al., 2020) needs a
separate \textasciitilde1 GB set of distilled databases, covering Spider
dev only. Its official download was over its quota at the time of
writing, so it is deferred to Part 3. Execution accuracy can therefore
still contain coincidental matches; §d.9 shows one.

\textbf{Harness metrics.} Our own harness
(\texttt{evaluation/metrics.py}) records four per-example outcomes for
every dataset:

\begin{itemize}
\tightlist
\item
  \emph{Strict EX} requires result-column labels (case-insensitive) and
  row order to agree as well.
\item
  \emph{EX with official semantics} ignores labels and compares rows as
  multisets.
\item
  \emph{Normalised string match} (SM) is whitespace-collapsed,
  lower-cased string equality. It is \textbf{not} Spider's EM, which
  explains the template's 0\% SM.
\item
  \emph{Invalid SQL} counts any SQLite error or empty prediction, and is
  decomposed by error class.
\end{itemize}

\textbf{Splits and uncertainty.} All development decisions were made on
Spider dev. \textbf{Spider test was run once}, after the configuration
was frozen. WikiSQL dev serves as a single-table diagnostic. Questions
on the same database are correlated, and Spider pairs most queries with
a paraphrase, so confidence intervals come from a bootstrap that
resamples whole \textbf{databases} (10,000 resamples, seed 42). Paired
comparisons report an exact McNemar test and a paired database-clustered
bootstrap. Holm's correction is applied across all comparisons in a
table. Per-question official outcomes are produced by
\texttt{scripts/official\_per\_example.py}, which mirrors the official
scoring loop and reproduces its totals exactly. Training was repeated 3
times (seeds 7, 13, 42) with the identical recipe, as replication runs
separate from Job 361547; we report mean ± sample standard deviation
across these seeds.

\textbf{Why also strict EX?} Strict EX also requires matching
result-column labels, which makes it sensitive to how an expression is
spelled. Quoting identifiers alone moved the template's strict dev EX
from 5.80\% to 7.06\%. It is reported only as a secondary diagnostic.
All conclusions rest on the official metrics.

\textbf{Sanity check.} Submitting the gold SQL as the prediction gives
\textbf{100\% strict EX} on Spider dev (1,034/1,034) and Spider test
(2,147/2,147) and WikiSQL dev (8,415/8,415). This check exposed one
harness bug, now fixed: two dev gold queries on \texttt{wta\_1} crashed
on non-UTF-8 text and could never be scored. Gold-equals-gold cannot
detect a gold query that runs but means nothing, so we also checked that
gold queries return real answers. That exposed a far more serious
WikiSQL bug, described in §d.11.

comparison changes several things at once. The table above isolates
repair on a single checkpoint. To isolate the epoch count, the
replication runs also saved a checkpoint after Spider epoch 10. With
identical (final) decoding, epoch 10 vs epoch 25 gives official EX 7.6 ±
1.1\% vs 7.5 ± 1.7\% on dev and 6.9 ± 0.8\% vs 7.6 ± 0.7\% on test;

\textbf{Schema linking.} Identifiers are extracted from each SQL string
after removing literals, as the words that match a table or column name
of that database (case-insensitive). Tables are the names after
\texttt{FROM}/\texttt{JOIN}. Precision and recall are micro-averaged
over all dev questions. For the LSTM, identifier precision/recall is
39.9\% / 40.4\% and table precision/recall is 46.8\% / 46.5\%. The
template is a purely lexical linker (question words matched to schema
names), so it serves as a lexical baseline: 68.5\% / 29.3\% for
identifiers and 69.4\% / 41.8\% for tables. The LSTM recalls more schema
elements than lexical matching but with far lower precision. Choosing
the wrong column or table is the dominant failure, ahead of syntax.

\textbf{Execution-match audit.} Execution hits that do not string-match
the gold SQL are classified automatically. A hit is \emph{equivalent}
when its literal-stripped signature equals the gold one; otherwise it is
\emph{coincidental}, split by whether the gold result is empty or zero.
Template: 14 structurally equivalent to gold; 13 coincidental (a gold
clause is missing or different); 6 coincidental (gold result is empty or
zero). LSTM: 15 structurally equivalent to gold; 10 coincidental (gold
result is empty or zero); 7 coincidental (a gold clause is missing or
different). For example,
\texttt{SELECT\ DISTINCT\ Country\ FROM\ singer} matches gold
\texttt{…\ WHERE\ age\ \textgreater{}\ 20} only because every singer is
over 20. The EM-confirmed EX column of the main results tables is the
corresponding conservative accuracy.

  \texttt{SELECT\ COUNT(*)\ FROM\ concert\ WHERE\ Year\ =\ 2014\ OR\ Year\ =\ 2015}.

  analysed separately in §c.5.

  official exact-set match also counts it correct. Our string match does
  not, because of the trailing semicolon.
\item
  \textbf{Projection omission} (\texttt{spider-dev-2}, medium):
  \emph{``Show name, country, age \ldots{}''} →
  \texttt{SELECT\ Name,\ Country\ FROM\ singer\ ORDER\ BY\ Age\ DESC}.
  Valid SQL; the third projected column is dropped.
\item
  \textbf{Schema-type token leak, then wrong column}
  (\texttt{spider-dev-4}, medium). Base decoding produced
  \texttt{…\ WHERE\ text\ =\ \textquotesingle{}france\textquotesingle{}}.
  That query is invalid: \texttt{text} is the serialised \emph{type} of
  \texttt{Country}, and the literal case is wrong. The final
  configuration produces
  \texttt{…\ WHERE\ Is\_male\ =\ \textquotesingle{}France\textquotesingle{}}.
  Casing and validity are fixed, but the column is still wrong.
  Rendering cannot fix schema linking.
\item
  \textbf{Aggregation error} (\texttt{spider-dev-494}, medium):
  \emph{``What is maximum and minimum death toll \ldots{}''} →
  \texttt{SELECT\ MAX(caused\_by\_ship\_id),\ MIN(caused\_by\_ship\_id),\ MIN(killed)\ FROM\ death}.
  The aggregate functions are plausible but attached to the wrong
  columns, plus an extra projection. Aggregation mismatches occur in 167
  failures.
\item
  \textbf{Join hallucination} (\texttt{spider-dev-24}, extra-hard). Gold
  joins \texttt{concert} and \texttt{stadium}. The prediction joins
  \texttt{singer\_in\_concert} and \texttt{singer} on
  \texttt{Singer\_ID\ =\ concert\_ID} and selects the nonexistent
  \texttt{t2.stadium}. It shows correct clause skeleton generation with
  no grounding in the foreign-key graph.
\end{enumerate}

\subsection{WikiSQL: a harness defect and a rendering
defect}\label{wikisql-a-harness-defect-and-a-rendering-defect}

A natural explanation for the LSTM's 0.04\% WikiSQL EX would be
catastrophic forgetting during Spider fine-tuning. \textbf{The run log
rules this out.} Job 361547 scored WikiSQL with
\texttt{wikisql\_checkpoint.pt}, saved at the end of Stage 1,
\emph{before any Spider training} (log line:
\texttt{Loading\ dataset-specific\ checkpoint:\ wikisql\_checkpoint.pt}).
The predictions are mostly sensible SQL in an unexecutable surface form.
For example,
\texttt{SELECT\ player\ FROM\ "table\_1\_10015132\_11"\ WHERE\ no.=\ 42}
should be \texttt{…\ WHERE\ "No."\ =\ 42}. Multi-word column names were
emitted unquoted and lower-cased (\texttt{school/club\ team}), and
repair v1 quoted only the first word of multi-word literals
(\texttt{=\ \textquotesingle{}concord\textquotesingle{}\ hs}). The fault
lay in the rendering, not the model.

\textbf{Harness defect.} The official WikiSQL database stores each
table's columns as \texttt{col0\ …\ colN}, with lower-cased text values.
Our loader, however, wrote gold SQL with the original header names, such
as
\texttt{SELECT\ "Position"\ …\ WHERE\ "School/Club\ Team"\ =\ \textquotesingle{}Butler\ CC\ (KS)\textquotesingle{}}.
SQLite treats a double-quoted name that matches no column as a
\emph{string literal}. Every gold query therefore executed without error
but compared constants: 6,007 of 8,415 dev gold queries returned an
empty result, and any prediction that also returned nothing counted as
correct. All earlier WikiSQL execution numbers, the template's 7.23\%
included, were therefore meaningless. The harness now creates, per
connection, a TEMP VIEW with the table's own name that exposes
\texttt{colN} under its header. Text columns compare case-insensitively,
mirroring the official executor, which lower-cases condition values.
With the view, 7,767 gold queries return real answers. The table below
re-scores the same predictions with the corrected harness.

\subsection{Demonstration (CLI)}\label{demonstration-cli}

\textbf{Live training.}
\texttt{uv\ run\ text-to-sql-demo\ -\/-train-demo} trains a small
pointer-generator (embedding 128, hidden 256) from scratch on the 95
Spider \emph{train} questions of \texttt{soccer\_2}, for 60 epochs on a
laptop CPU, which takes about 2--3 minutes. It prints the per-epoch
training and held-out NLL. It decodes a probe question with random
weights before training and again after. It then reports execution
accuracy on 20 questions the model trained on and on 11 held-out
questions from the same database. In our rehearsal the loss fell from
4.88 to 0.09, and the model scored 15/20 on seen questions but 0/11 on
held-out ones. That is the memorisation gap of §d.3 at small scale. The
saved checkpoint can be queried at once with
\texttt{-\/-model\ lstm\ -\/-checkpoint\ artifacts/train-demo/spider\_checkpoint.pt}.

\textbf{Inference.} \texttt{-\/-demo\ -\/-model\ template} runs a
scripted three-case showcase on \texttt{concert\_singer}: a count, a
filter, and a graceful failure on an unsupported join.
\texttt{-\/-model\ lstm} loads the evaluated Job 361547 checkpoint with
the final decoding configuration.
\texttt{-\/-question\ "…"\ -\/-database\ \textless{}path\textgreater{}}
answers any question and prints the SQL and the result table. For Spider
databases, the CLI builds the schema from \texttt{tables.json}, so the
serialisation matches training exactly.
\texttt{scripts/show\_preprocessing.py} prints the pipeline stages of
§c.4 for any example. The proposal planned a GUI; the Part 2 interface
is this CLI, which the course rubric explicitly allows (``results should
be shown through a GUI or CLI'').
